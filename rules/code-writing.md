# 코드 작성 기준

시니어 개발자가 리뷰에서 지울 코드는 처음부터 쓰지 않는다.

## 검증과 방어는 경계에서 한 번

- 신뢰 경계에서 검증·정규화하고 에러를 처리한다. 신뢰 경계는 사용자 입력, HTTP 요청, CLI 인자, 설정·환경변수, 외부 API·파일·DB에서 읽은 값이다.
- 경계를 통과한 내부 데이터는 다시 검증하지 않는다. 호출부나 타입이 이미 보장하는 값에 null 검사, 타입 검사, try/catch를 덧대지 않는다.
- 방어 코드는 그 상태가 실제로 생길 수 있을 때만 둔다. 생기면 안 되는 상태라면 가드로 숨기지 말고 그 상태를 만든 곳을 고친다.
- 에러를 삼키지 않는다. 빈 catch, 기본값으로 덮기, 로그만 남기고 진행하기가 모두 해당한다. 처리할 수 없는 곳에서는 위로 올린다.
- 보안 방어는 줄이지 않는다. 출력 이스케이프, SQL 파라미터 바인딩, 인증·인가, 비밀값 처리는 지킨다. "경계에서 한 번"은 같은 방어를 층마다 반복하지 말라는 뜻이다.

## 주석

- 코드로 드러나지 않는 "왜"만 한 줄로 남긴다. 무엇을 하는지 설명하는 주석, 단계 나레이션, 변경 이력이나 리뷰 반영 여부는 쓰지 않는다.
- 예외는 보안 판단의 근거, 의도된 트레이드오프나 알려진 한계, 지우면 조용히 깨지는 코드다. docblock API 문서는 대상이 아니다.

## 테스트와 검증

- 테스트는 호출자가 관찰하는 동작을 검증한다. 내부 호출 순서, private 헬퍼, 문구를 고정하지 않는다.
- 실패를 먼저 확인하는 TDD는 사용자가 요청했거나, 재현한 버그에 싼 테스트 경로가 있을 때만 쓴다. 그 외에는 구현한 뒤 기존 테스트나 기능 단위 확인으로 검증한다.
- 함수마다 테스트하지 않는다. 목만 검증하거나 구현을 복제하는 테스트는 없는 편이 낫다.
- 검증은 수정을 모은 뒤 기능·파일 단위로 한 번에 한다.

## 단순함

- 요구된 것만 만든다. 구현이 하나뿐인 인터페이스, 호출자가 하나인 래퍼, 쓰이지 않는 설정이나 확장점을 만들지 않는다.
- 이미 있는 헬퍼와 패턴을 재사용하고 주변 코드의 스타일을 따른다.
